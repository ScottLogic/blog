## Evals

AI functionality let us build systems that handle open-ended tasks no deterministic function could. That capability comes with a trade-off: Large Language Models (LLMs) are non-deterministic, so the same input can produce different outputs. This can make their behavior hard to predict and, as a result, hard to test.

That's where Evals come in. In a deterministic system we assure quality by writing tests, we isolate functionality and assert that a given input produces the expected output. With an agent we can't rely on this 'exact match' style of testing alone, so we need a different approach. Rather than asserting that the output is correct, we define what good looks like for our specific use case, i.e. a set of criteria that, taken together, describe a good quality response. This means Evals are bespoke to the problem an agent is designed to solve. What good looks like differs from agent to agent, and so do the criteria.

An Eval works like this. We give the agent an input, then capture its response and, ideally, a trace of what happened while it performed the task e.g. how many times the LLM was called, which tools were called and how often etc. We then run a set of scorers against that output. Each scorer checks one aspect of quality and falls into one of two categories:

<div style="background-color: #dff4f5; padding: 1em; margin-top: 2em; margin-bottom: 2em">
<h3 id="deterministic-scorers">Deterministic scorers</h3>
<p>These are standard functions, with no LLM involved, that check one aspect of the output, such as "how many tool calls were made?" or "does the output contain an expected keyword?".</p>
</div>

<div style="background-color: #dff4f5; padding: 1em; margin-top: 2em; margin-bottom: 2em">
<h3 id="non-deterministic-scorers">Non-deterministic scorers</h3>
<p>Usually LLM-as-a-judge: we give the agent's output to a different LLM and ask it to rate the response against some criteria. For example, we might ask the judge to rate the tone of a customer-facing agent, or to check that a decision is backed by reasonable evidence. The judge should use a different model, and ideally a different provider, from the LLM under test so the model isn't marking its own homework.</p>
</div>

<img alt="Eval pipeline" src="{{site.baseurl}}/dogle/assets/evals-fluxnova/eval_pipeline.png" title="Evaluation Pipeline Diagram" style="display: block; margin: 0 auto; padding: 1rem 0;" />

Finally, we need to define what an acceptable score is. Some scorers are a simple pass or fail while some, such as one assessing the quality of evidence, return a percentage. We set thresholds for what counts as a pass, both for each scorer and for the system as a whole.

For example, bellow is an example of some deterministic and non-deterministic Scorers:

| Scorer | Type | Checks | Pass |
| --- | --- | --- | --- |
| `final_recommendation_format` | Deterministic | The last line is exactly `APPROVE` or `REJECT` | true / false |
| `tool_correctness` | Deterministic | The agent called exactly the tools this applicant's profile requires | score 0.0–1.0 |
| `step_efficiency` | Deterministic | At most four LLM calls (five with collateral) | true / false |
| `decision_quality` | LLM judge | A definitive decision backed by concrete evidence from the tool results | yes / no |
| `evidence_citation` | LLM judge | The output cites the fraud score, affordability outcome and income evidence | score ≥ 0.7 |

Evals give us confidence in an agent both in development and in production.

In this post I'll use a loan approval process for an example. All of the code, BPMN models and Evals are available in the accompanying [repository](https://github.com/ScottLogic/fluxnova-eval-demo).

## Eval Driven Development

Eval Driven Development (EDD) applies the ideas of [Test Driven Development (TDD)](https://agilealliance.org/glossary/tdd/) to agentic systems. We define what good looks like upfront, as a set of Evals, and then develop the agent until it meets that standard.

While developing an agent we want two things: a definition of what the agent should be able to do, and assurance that changes don't break existing behavior. In a deterministic system TDD gives us both. We write tests that describe the functionality we want, then write code until they pass. That gives us a hill to climb (a clear idea of when the system behaves as expected) and a regression baseline that tells us when we've broken something. EDD gives us the same two things for an agent.

In development we don't have live traffic, so we need to supply inputs to agents ourselves. To do this we build a set of Golden Scenarios which are inputs ideally drawn from real world cases, each paired with an example of a good response, often written by a subject matter expert.

Here is one of the demo's Golden Scenarios. It describes the input and the answer an expert would expect along with some metadata such as the responses each tool should return so we can mock the scenario correctly:

<img alt="Golden" src="{{site.baseurl}}/dogle/assets/evals-fluxnova/golden.png" title="Golden Dataset Example" style="display: block; margin: 0 auto; padding: 1rem 0;" />

Our regression suite then runs each Golden Scenario through the agent, captures the output and runs the Scorers against it. Alongside the other Scorers, we can give the expert's reference response to an LLM judge and ask it to compare the agent's answer against it.

Not all scorers are equal. Just as the scorers must be bespoke to the use case, the set of scorers we run should be chosen per scenario. LLM-as-a-judge scorers are expensive compared with deterministic ones, in both time and tokens: each one means a round trip to an LLM, which is far slower than running a function, and those calls add up quickly when we run several judges per response.

In regression testing we want to prioritise depth, we often care less about the time taken to run the tests or even the associated cost than we do about getting as much feedback as we can on our agent's response. We will usually run several LLM judges here, because we want as much confidence as possible before the agent reaches production. We can also run scorers that would couldn't in production. Because we know the input and the expected output in advance, we can check things that rely on that knowledge, for example asserting that a particular tool was called for a scenario we know requires it.

What we end up with is a suite of regression tests built around Golden scenarios which capture the breadth of use-cases we expect our agentic system to be able to handle. We score each sceanario with as many Scorers as we can to fully capture all aspects of the output quality we can and gain confidence that our system meets our threshold for quality a high percentage of the time.

## Evals in Production

Once things move to production our scenario changes slightly, in production we usually don't know the input in advance. Agents are good at handling free-form, varied input, so production input typically comes straight from users rather than from a known set of scenarios. However well the agent did in regression testing, we still need to evaluate its output in production, to understand the quality of response across the full variety of real-world cases it handles.

To do this we need to capture the agent's response and trace so we can score them. There are several ways to capture this data; a common approach is telemetry, recording metrics and traces using a standard such as the [OpenTelemetry GenAI semantic conventions](https://github.com/open-telemetry/semantic-conventions-genai). An example of what the tracing looks like is:

<img alt="Tracing" src="{{site.baseurl}}/dogle/assets/evals-fluxnova/tracing.png" title="gen_ai execution tracing shape" style="display: block; margin: 0 auto; padding: 1rem 0;" />

We can then run scorers against the captured data. The production Scorers we use will differ from the development set: scorers that depend on knowing the input in advance won't work, and we will probably want fewer LLM judges.

On a heavily used system, scoring every trace may not be practical, so we would typically score a sample to build a view of quality over time. Even then, several LLM judges per sampled trace can become costly, so it pays to be selective with them in production.

In short, regression testing optimises for depth of confidence, while production Evals optimise for breadth of coverage at a sustainable cost.
In the demo, the scorer sets compare like this:

| Scorer | Regression | Production |
| --- | --- | --- |
| `decision_quality` (LLM judge) | ✓ | ✓ |
| `matches_golden` (LLM judge) | ✓ | ✗ needs an expected answer |
| `evidence_citation` (LLM judge) | ✓ | ✓ |
| Tool-use and output checks (deterministic) | ✓ | ✓ |
| Tool-argument checks (deterministic) | ✓ | ✗ we must know the scenario in advance |

Over time, production Evals will build a picture of what the agent handles well and where it underperforms. 

We can then feed this back into our regression suite to close the loop: take common failing cases, turn them into new Golden Scenarios with expert reference answers, and improve the agent until it passes them, while the existing suite tells us we haven't made anything else worse.

<img alt="Eval Loop" src="{{site.baseurl}}/dogle/assets/evals-fluxnova/eval_loop.png" title="Evaluation Loop" style="display: block; margin: 0 auto; padding: 1rem 0;" />

So far we've treated Evals as a way to observe quality but we can go further, and let the result of an Eval change what the system does next. This is where a workflow orchestration engine can be valuable.

## Fluxnova

[Fluxnova](https://fluxnova.finos.org/) is an open-source, community-maintained workflow orchestration engine, hosted by [FINOS](https://www.finos.org/) and forked from Camunda 7. It lets you model processes as BPMN diagrams (stored as XML) and run them. This brings several benefits:

- Processes are modelled visually in the BPMN Modeler, which makes them accessible to non-technical domain experts as well as developers.
- Workflows can be deployed and started from a UI or through an API.
- Every run is recorded, making it straightforward to audit and trace what happened.
- Crucially for this post, adding service tasks and human-in-the-loop steps to a process is simple.

One of the plugins available for Fluxnova that Scott Logic helped to develop is the [agentic ad-hoc subprocess plugin](https://github.com/finos/fluxnova-plugins/tree/main/agentic-subprocess). Put simply, it gives an agent control of a ring-fenced section of the process. In our loan example, the agent controls the risk assessment step.

The agent is given a prompt embedded into the bpmn, such as this (abridged):

~~~text
You are a senior loan assessment analyst. Your goal is to gather enough evidence to make a well-reasoned, defensible lending decision for each applicant. You MUST complete ALL required checks before stopping, even if an early result is unfavorable.

Execute in rounds:
(1) Call Run Fraud Screening and Check Credit Score together in the SAME tool-calling response.
(2) For EMPLOYED applicants, run Verify Employment; for SELF_EMPLOYED applicants, run Analyse Bank Statements instead. If hasCollateral is true, also run Value Collateral. Never value collateral when hasCollateral is false.
(3) Run Assess Affordability only after the income-verification tool has completed.
(4) Once all required tool results are available, provide your final response.

The target is at most four total LLM calls including the final answer, or five with a separate collateral round.

Your final response must first summarize the actual evidence ... Then give a concise justification explicitly connecting those values to the selected decision ...

Finish with a NEW final line containing EXACTLY APPROVE or REJECT.
...
~~~

The full prompt is in [`bpmn/loan-assesment.bpmn`](https://github.com/ScottLogic/fluxnova-eval-demo/blob/main/bpmn/loan-assesment.bpmn) in the demo repository.

The agent is also given a set of tools, each modeled as a service task, which it can call in any order and as many times as it likes. It alternates between LLM calls and tool calls until it decides it has an answer, then completes the subprocess.

Much of this prompt maps directly onto scorers. "At most four total LLM calls", "the right income-verification tool for the employment type", "never value collateral when hasCollateral is false" and "a final line containing exactly APPROVE or REJECT" are all deterministic checks, while "a concise justification explicitly connecting those values to the selected decision" is a natural fit for an LLM judge. We capture as closely as we can that the agents output aligns with the prompt it was given.

## Evals with Fluxnova

As with any system, to evaluate an agent running in Fluxnova we first need to capture its output.

### Keeping sensitive data out of the telemetry

We could use telemetry, as described above, to capture this output but we may not want sensitive data such as `gen_ai.system_instructions`, `gen_ai.input.messages` and `gen_ai.output.messages` to end up there. It's possible to encrypt the data, but telemetry platforms are built for broad access (dashboards, wildcard queries, long retention), which is the opposite of what we want for personal data.

Fluxnova offers an alternative. Process variables carry data from one step of the workflow to the next, so the agent's output can travel through the process itself. It is then governed by the same access controls and audit trail as the rest of the process data, rather than being sent to a telemetry platform. This is powerful as it means we can easily capture the output from the agent without exposing sensitive data as telemetry.

### EDD with call activities

For regression testing, we model the agentic subprocess as its own small BPMN process. That lets us test it in isolation while still including it in the parent process as a [call activity](https://docs.fluxnova.finos.org/manual/3.0/reference/bpmn20/subprocesses/call-activity/). The subprocess returns its output as process variables, which the test can then read.

For each Golden Scenario we deploy the BPMN and start it with the scenario's input variables. Because the agent's tools are plain service tasks, mocking them only requires registering mock workers that return the scenario's predefined responses. We then read the agent's output and run our scorers against it as before.

The mock responses come straight from the Golden Scenario's `tool_responses`. In the scenario above, the `fraud-screening` worker returns `{ "fraudRiskScore": 78 }`, so the agent receives exactly the evidence the expert based their answer on.

### Non-blocking Evals in production

In production we can leverage the workflow itself, by adding an Eval service task directly after the agentic subprocess. The process passes the agent's output to this task, which triggers the Evals without holding up the process. This gives us the same view of production quality as before, but the agent's inputs and outputs are read from process variables rather than from exported telemetry.

In the demo, a parallel gateway after the agent splits the run in two. One branch continues with the loan process. The other goes to an `Eval: Record Agent Output Scores` service task, which scores the output and records the results. The two branches never rejoin, so the loan decision never waits for the Eval.

## Evals and Guardrails

So far our production Evals are retrospective, they give us a view of how the system has behaved in production and allow us to build forward based on that view. We could go further than this and make them act by adding a blocking call to an Eval service in our application code. We can take the agent's output, wait for the Eval result and use it to decide what happens next. This works, but it hides an important business decision, namely when the agent's output can be trusted, inside application code. The logic is invisible to the people who own the process, can only be changed with a code release, and any human review it triggers has to be built, tracked and audited by hand.

Because the Eval is already a step in a BPMN process, Fluxnova gives us a better option. We can create a version of the Eval task that blocks. The process waits for the Evals to complete and a gateway then routes the process based on the result. In this way the Eval now becomes a guardrail.

<figure style="text-align: left; margin: 2rem 0;">
  <h4 style="margin-bottom: 1rem;">Guardrail Implementation splits the flow to divert to a user task if certain conditions are met</h4>
  <img alt="Guardrail" src="{{site.baseurl}}/dogle/assets/evals-fluxnova/guardrail.png" title="Guardrail Implementation" style="display: block; padding: 1rem 0;" />
</figure>

With this in place we can do things such as:

- Divert the process for human review when the Eval fails or falls below a confidence threshold, sending the case to a user task where a reviewer can approve, amend or reject the agent's decision before the application continues.
- Apply the guardrail to a sample of runs, so we only pay for blocking Evals on a proportion of traffic.
- Require human review on every nth run regardless of score, to keep an independent, ongoing check on the agent.

The Eval task's handler is ordinary code, so we can implement the scoring however we like. The routing, though, lives in the process model rather than in that code, so it inherits everything Fluxnova already provides:

- The guardrail is visible and versioned in the BPMN, so anyone can see exactly when the agent's output is trusted and when it isn't.
- Routing, and thresholds passed in as process variables, can be changed in the Modeler without touching the Eval service.
- Every Eval result and every human decision is recorded in the process history.
- Human-in-the-loop is a native user task rather than something we have to build.

In the demo, the guardrail's settings are input parameters on the `Evaluate Agent Output` task. Each one takes the value of a process variable if the run sets one, and falls back to a default otherwise:

<figure style="text-align: left; margin: 2rem 0;">
  <h4 style="margin-bottom: 1rem;">Guardrail Settings as seen from the Fluxnova Modeler</h4>
  <img alt="Gaurdrail Settings" src="{{site.baseurl}}/dogle/assets/evals-fluxnova/modeler_output.png" title="Gaurdrail Settings in Fluxnova Modeler" style="display: block; padding: 1rem 0;" />
</figure>

- `evalMinScore` is the fraction of applicable scorers that must pass.
- `evalRequiredScorers` lists scorers that must pass whatever the overall score.
- `evalSampleRate` is the fraction of runs the guardrail scores.
- `forceReviewEveryN` sends every Nth run to review regardless of its score.

The Eval worker returns `evalPassed`, `evalScore`, `evalFailedScorers` and `evalRationale`, plus a `reviewRequired` flag and a `reviewReason` of `FAILED_EVAL`, `FORCED_EVERY_N` or both. The gateway after the task routes on `reviewRequired`.

When a run is sent for review, the `Human: Risk Assessment Review` task shows the reviewer the agent's assessment, the tool evidence and the guardrail's rationale. The reviewer can then choose one of four options:

- **Approve**: keep the agent's decision.
- **Amend to approve** or **amend to reject**: replace the agent's decision.
- **Reject**: don't accept the assessment, and decline the loan.

The process records the choice as `reviewOutcome` and `reviewDecision`, and the next gateway uses the reviewers decision instead of the agent's. The scores, the reason for review and the reviewers decision all end up in the process history.

## Conclusion

In order to have confidence in the agentic systems we build we need a different approach to quality assurance. Evals go some way to providing this confidence. In development, EDD with a suite of Golden Scenarios give us a target to build towards and a baseline for catching regressions, allowing us to understand what our system does well and when we have introduced regression. In production, Evals show us how the agent copes with real-world input, and the cases it struggles with can become new Golden Scenarios, giving us a continuous loop of evaluation, development and deployment.

Running the agent inside a workflow orchestration engine such as Fluxnova takes this a step further. Sensitive data can stay in the process rather than being exposed via telemetry, every run is auditable, and we can take this further and rather than Evals being a passive measurement make them an active guardrail. We create a visible, versioned step in the process that allows us to bring a human into the loop as we decide is necessary based on our requirements and the concrete evidence we get from our bespoke Scorers.

All of the code, BPMN models, Golden Scenarios and Scorers described in this post are available in the [demo repository](https://github.com/ScottLogic/fluxnova-eval-demo).
