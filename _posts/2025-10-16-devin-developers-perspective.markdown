### **Introduction**

When I first started experimenting with Devin, I wasn’t sure what to expect. The promise of an AI-powered development assistant sounded compelling, but I wanted to test it in a real-world scenario. I chose to revisit a sustainability project we’d previously shelved. I began work on a set of carbon emissions calculators to see how far I could get using Devin as my primary development partner.

## **From Spreadsheet to Production-Ready Tool**

The original sustainability project had stalled due to over-complication and misaligned goals. We were using spreadsheets to estimate emissions in a collaboration with the Green Web Foundation, but the process was error-prone and lacked scalability.

In just over a week, I transformed those spreadsheets into a fully functional web application. Devin helped me implement all the original calculators, add two new ones, build a dashboard, and integrate export functionality, including support for the Tech Carbon Standard (TCS) schema.

It felt like having my own development team.

## **My Journey**
### **A Shaky Start**

I began my exploration of Devin not knowing anything about it. I've been developing software for over 15 years. In the last year, I've been learning about AI assisted tools such as ChatGPT and Github Copilot, but I had no real understanding of how Devin differed from these tools other than it was intended to be more independent.

I began by attaching a copy of the Excel workbook to the Devin session. I then gave it a deliberately vague prompt just to see what it would do. I asked Devin to convert the attached spreadsheet into a Electron app.
![Screenshot of a spreadsheet viewer generated by Devin]({{ site.github.url }}/uploads/devin-spreadsheet-viewer.png "A Devin generated spreadsheet viewer")

This, as expected, failed in several ways, but the results were very interesting. First of all it told me that because it was an Electron app, it wouldn't be any to interact with it fully, so I'd have to validate the output myself. Intriguing! It also just produced a non-editable spreadsheet viewer that was of very little use. 

I also realised that it needs a repo to work with which we hooked up through the back end.

## **The Workflow**

At this point, I should probably describe the workflow I was using with Devin a bit more fully.

First, you point Devin at a repo, tell it what it is for, and what you want to change. Devin then does some analysis, examines the repo and what it knows about the request and summarises a plan, with a confidence level (low, medium or high). If the confidence level is below high, it will widen its analysis to try and improve it's confidence in the plan and may ask the user clarifying questions. I found this very impressive, as I've not seem LLMs admit they are not sure before! 

![Screenshot of Devin's confidence output]({{ site.github.url }}/uploads/devin-confidence.png "Confidence output from Devin")

Once a plan is decided upon, it will spin up a VM, create a branch of the repo and start implementing and (if possible) testing the feature. Once it is finished it raises a PR. 

You can interact with Devin in a variety of ways, including the web chat interface, via a ticket system such as Jira, or via comments on a PR.

You then have the opportunity to review the PR and can interact with Devin to address any issues before merging it into main.
## **Trying Again...**

Having failed to produce anything useful with my first prompt, I started again, with a slightly better understanding of how I should work with this tool.

This time I changed from Electron to a simple TypeScript/React software stack. This would allow Devin to interact with the solution in real time and help it to produce better results. I also expanded my prompt to explain what I wanted and asked it to focus on creating just models for the calculations.

It put together a basic structure and we iterated over some technical details - it had brought in a bit too much and the node package install was taking a long time.

Still, a much better starting point.

Following this we worked together to add unit tests, round out the models and calculations and ensure a maintainable solution.

# **Observations**
I found this experiment very encouraging. Here are some observations from myself and from a feedback session that followed the work:
- **Speed and completeness**: We were impressed by how quickly the tool came together. In just seven working days we had a complete sets of calculators, that incorporated live carbon intensity data and some useful utilities such as import/export. There are a robust set of both unit and end to end tests.
- **Validation concerns**: Given the volume of code that  Devin produces, it can be very challenging to verify its output. I found that I could not read every single line of code. Instead I focused on important areas of logic rather than the UI and used testing to verify the output. I also found value in using other tools (both AI based and static analysis such as linting) to assess the code
- **Design polish**: Devin produce a good UI design that I was able to apply branding to easily.
- **Design Bloat**: Left to its own devices, the code quickly became bloated and the design drifted. I had to examine its output and get it to refactor the code to account for this.
- **Technical debt**: Another side effect of this is that, given free reign, LLM based code generation will bake in large amounts of technical debt from minute one of the project. It doesn't always look a the full project or make long term decisions - it will give you what you ask for, not what you need.
- **Refactoring is cheap**: That said, refactoring large changes is much easier in Devin. For example, after adding a few calculators I could see the code base was getting large and there was a lot of repetition. I prompted Devin to analyse the codebase with an eye to this problem to which it produce a comprehensive refactoring plan that I reviewed and agreed with. I fed this plan back into it in chunks to apply the refactor, which reduce the size of the project by about 60%. 
- **Context size management**: It is important in Devin to start new sessions regularly to stop context rot. It takes a little experimentation to get a feel for when it is better to let a session size grow and when to start a new session.
- **Context switching**: I found that, due to Devin's iterative workflow, it was far too slow to sit and watch. On the other hand, it was fast enough that I couldn't really get stuck into other tasks without being interrupted to set it onto its next step. There are a few strategies that helped here:
	- **Fire and forget**: Some tasks don't need to be looked at right away - for example fixing a small bug. I could create a session to investigate and fix and but and look back in on it at a time that was good for me - Devin will happily sleep while it waits for you.
	- **Parallelization of tasks**: Provided there is no sequential dependency between tasks, you can start several sessions and have Devin working on them at the same time - it will spin up the VMs and feature branches it needs to do that. This way I was able to review the output of one task while a few others were still running.
- **Cost concerns**: Devin uses a pay as you go model. I found it easy to set off tasks and not really know the cost of what I was doing. We had to top up our account multiple times, which made it feel a bit like my kids spending Fortnite V-Bucks and having no real concept of the value of what they were spending.

## **Comparing Co-pilot and Devin**

When working with Co-pilot I found that I needed to reign it in to get good output. Given too much freedom it would over produce inappropriate code for the problem at hand and go down paths that I wanted to avoid. I found the trick to working with it was to limit it's focus and context, direct it on code style and pattern to get the best results. Treat it like a junior dev and code review the output. Keep PRs small and submit them for review by other team members to keep the quality high. Don't swamp your team mates with reams of AI generated code - that will lead to them tuning out and bugs and bad design decisions will slip through.

By contrast, this approach worked very poorly with Devin. I found I had to embrace the volume and run with it. I focused on the main logic and spotting larger code design issues. Then I would direct Devin to analyse and refactor the solution. This worked surprisingly well, as it was able to work quite independently and make changes to large parts of the codebase rapidly. 

## When to AI Tools

While the output is impressive, it doesn't replace engineering skill - it augments it. Like any tool, appropriate application is critical.

For business critical applications and business logic, skilled software engineers are still the best and safest approach. That said, tools like Co-pilot can certainly relieve some of the cognitive burden and allow the engineer to focus on the logic over the syntax. However, without hands on experience, they will not be able to critically assess the output of the tool. I would recommend against encouraging junior developers to use these tools to give them that experience to use them well later in their careers.

Devin could, of course, be driven by any user with an idea and enough business knowledge to describe how to do it. This temptation should be resisted. As stated above, without the engineer's involvement, the product will be plagued by hard to track bugs, security flaws and an unwieldy codebase that even the AI will find it hard to keep in context.

For greenfield development, at the start of the project, I found Co-pilot helpful, but Devin clumsy. At the start of the project there is a certain level of maturity before you can move away from interdependent tasks, which resulted in lots of waiting for it to finish before moving onto the next stage. Co-pilot, on the other hand, could be used to automate small bits of boilerplate and scaffolding.

Devin took off once that level of maturity was reached. Then I could use it for self contained features, bug fixes and adding test automation. All of these could be done in parallel and merged when I was ready.

So, for greenfield development, start with a real team of people, optionally using AI augmentation such as Co-pilot. Then, bring Devin online to accelerate the deliver at an appropriate point. For example, in a recent project, we had to make a major change to the auth system that broke all the Playwright tests. The testers had to update a large number of tests to restore their test suite before they could proceed. This mean that new features hit a bottle-neck. If we had a system like Devin, we could have set Devin to correcting the Playwrite tests while our testers focused on the higher value work of checking our new features. 

I can also see Devin being very effective for creating and maintaining standard end to end tests. That way the testers can focus on critical features. Similarly, on the development side, there may be value in getting Agentic AI to perform bug fixing, whilst the team focuses on feature development.

Finally, in the hands of non-engineers, such as designers, product owners and entrepreneurs, Agentic AI can be used to rapidly prototype ideas to play with them before engaging the real development team. But don't be fooled into think that a prototype or proof of concept created in this way is appropriate in an way, shape or form to be delivered to production! 

## **Key Insights**

This experiment yielded several key insights:

- **Devin is a productivity multiplier**, but only when paired with strong engineering discipline.
- **Validation is non-negotiable** — especially for logic-heavy applications.
- **AI-generated code can be overwhelming**, and tools like Copilot or Claude are essential for review.
- **Design and UX still benefit from human input**, even when AI handles the scaffolding.

## **Conclusion**

Devin is a powerful tool, but it’s not a shortcut to good software. It’s a force multiplier for developers who know how to guide it, validate its output, and maintain what it builds. Used wisely, it can dramatically accelerate delivery, but it still needs a human engineer in the loop.
